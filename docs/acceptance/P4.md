# P4 acceptance: Codex

Manual checks for P4: the Codex adapter through the shared app-server daemon, discovery and
history, stored and live modes, model / effort / permission modes, idle close, steering, approvals
and questions through the broker, subagent threads, and the shared terminal (`codex resume` beside
Tether's own connection). Each check gives exact steps and the expected result. "Desktop" means a
browser window at least 1024 px wide; "phone" a real phone, or a browser at 375 × 812 with touch
emulation.

Phase acceptance (SPEC §11):
- P1–P3 acceptance passes on Codex (sections A–F, I–K below mirror them).
- The only core differences come from capability flags (§ L).
- Typing in the TUI and in Tether on the same thread both work (G2, G3).
- An approval answered on either side clears on the other (G5, G6).
- Approval fan-out and cross-connection steer, verified on real turns (G5–G7, D4).

## How Codex runs under Tether

- Tether never starts its own `codex app-server`. It connects to the user's **shared daemon** at
  `~/.codex/app-server-control/app-server-control.sock` (WebSocket over a Unix socket; Tether does
  the HTTP upgrade itself), one connection per live thread plus one shared connection for discovery
  and history. `CODEX_HOME` moves the socket with Codex's home. If the socket isn't there Tether runs
  `codex app-server daemon start` once; it never stops or restarts the daemon. Under systemd that
  start runs in a transient scope of its own (`tether-codex-daemon-…`), so the daemon outlives the
  runner's KillMode=mixed unit (`scripts/check-codex-daemon-scope.sh`, on a throwaway daemon).
- Threads live in the daemon, so a turn keeps running while the runner restarts; the runner
  rejoins it at start (`capabilities.persistent`), and the daemon asks pending approvals again.
- Capabilities: `canSteer: true`, `terminal: "shared"`, `subagents: { view: true, stop: true,
  steer: "via-parent" }`, `persistent: true`.
- **Permissions** are one menu of presets (Codex's approval policy + sandbox): **Read only**
  (on-request, read-only), **Ask first** (untrusted, workspace-write), **Auto** (on-request,
  workspace-write; Codex's own default), **Full access** (never, danger-full-access). Approvals are
  always routed to clients (`approvalsReviewer: "user"`), so they reach Tether's broker (and Codex's
  TUI when it's open) rather than Codex's automatic reviewer from `config.toml`.
- **Effort** comes from the model's list (Low, Medium, High, Extra high, Max, Ultra). A new session
  starts with the folder's Codex config (e.g. High): set Effort before the first message if you
  want it cheaper.
- **A thread keeps its own settings.** An existing thread shows the model, effort and permissions
  it last ran with (its rollout's newest `turn_context`), and opening or sending to it changes
  none of them. A combination that isn't one of the presets shows as it is (e.g.
  "never+read-only") and is never loosened. A thread with no turn yet shows what Tether started it
  with (remembered in `<config dir>/codex-threads.json` until its first turn), else Mode
  **Unknown**: never Codex's config, which may not be what the thread has.
- **A change you make in Tether** (model, effort, mode, also "Default") goes to the thread with
  `thread/settings/update` and counts as applied only once the daemon confirms it
  (`thread/settings/updated`; for a value the thread already has, from what it last said):
  - **Live:** the header shows the change at once. If Codex rejects it, doesn't answer within 30 s,
    or doesn't confirm it within 10 s, it's rolled back on every device (the header goes back to what
    the thread runs) and the device that made it is told "Codex didn't take that setting (…). It's
    unchanged."
  - **Stored:** it's kept and applied after the thread is joined at the next send (the daemon
    ignores settings passed to `thread/resume` when another client, e.g. Codex's TUI, has the
    thread loaded), and confirmed before anything is sent; if not, that send fails with "Codex
    didn't apply your permissions. Nothing was sent." (or "didn't confirm"). A mode change on a
    stored session also looks for what it left running (B5u): if a command is still up, the thread
    is joined then, with no turn, and the change is applied at that join.
  - **Every send** pins what's shown on `turn/start` (below), so it doesn't wait for a live change
    still unconfirmed: the turn runs what's shown either way. A change that then fails rolls back
    as above, and what a later send pins is what's shown then.
  - **Before a thread's first turn** what it started with is applied again at a join, unless a
    setting was confirmed since: that always beats it, and a resume is never looser than the last
    confirmed setting. It doesn't loosen a thread tightened since, either.
  - **The guarantee (what's running):** Tether keeps a set of what runs on the thread right now,
    the main turn, each subagent and each command left in a background terminal, each with the
    settings it really runs with: those pinned on a
    turn Tether started (`turn/start` carries the shown model, effort, approval policy, sandbox and
    reviewer, so a turn Tether starts runs exactly what's shown), else the daemon's own reports (the
    turn's `turn_context` in the rollout, the thread's `thread/settings/updated`, a subagent's own
    rollout). Never inferred from what Tether shows. If anything in the set runs looser than shown,
    the header says so ("This turn still runs with …" or "A subagent still runs with …") and offers
    Stop, which interrupts them and ends the commands their own turn left running in Codex's
    background terminals (interrupting a turn alone doesn't end a command already running in one).
    On the main thread only those: a command from an earlier turn (a dev server) goes on. A
    stopped subagent's thread is its own, so all it left running ends. When the note is about a
    subagent the button is **Stop the subagent** and stops only that thread. Turns
    starting or ending never clear another entry: each clears when its own thing ends
    (a subagent keeps its turn's settings after that turn ends, through new turns and restarts).
    Commands in background terminals (on the thread or a subagent's) keep the settings of the turn
    that started them too: when they have more access than shown there's one note ("A background
    command still runs with …", "N background commands …") and **Stop the command(s)**, which ends
    exactly those. A plain Stop never ends more than the above, so a dev server from an earlier
    turn runs on, under the note, until you press it.
  - **Fail closed:** settings Tether can't read (no `turn_context` found, even reading the whole
    rollout) show as **Unknown**; settings it can't express exactly show as **Custom**: a granular
    approval policy, a sandbox with network access or writable roots beyond the folder, or a permission
    profile of your own (Codex's built-in `:read-only`, `:workspace` and `:danger-full-access`, which
    the TUI's `/permissions` sets, are just their presets). Both count as looser:
    while something runs with them the note and Stop show, even when Custom or Unknown is also what
    the header shows (Tether can't pin those on a turn).
  - **Auto from Tether is exactly Auto:** picking a preset in Tether sets that sandbox with no
    network and no extra writable roots. A thread whose network you turned on elsewhere shows as
    Custom until you pick a mode in Tether, which turns it off again.
  - **"Approve for me"** (`approvalsReviewer: auto_review`, Codex's own reviewer answering
    approvals) is part of the mode: "Auto (Codex reviews)". It counts as looser than the same mode
    with you answering. Set elsewhere, it shows; a mode picked in Tether puts approvals back with
    you, and the next turn is pinned with it.
  - **A send never passes for pinned when it isn't.** A send to a thread already running a turn
    (another client's) is refused as busy, checked again right before `turn/start`. In the narrow
    race where the other client's turn starts between that check and `turn/start`, the daemon puts
    the message into that turn (it doesn't refuse `turn/start` on a busy thread): Tether says so in
    the transcript ("Your message went into a turn started elsewhere…") and shows that turn's own
    settings from its turn_context, with Stop when they're looser. What Tether pins only counts
    once the turn's own turn_context confirms it.
  - **Late confirmations:** if Codex applies a change after Tether rolled it back (a slow daemon),
    the header shows the true value and the transcript says "Codex applied your earlier change to
    the mode after all."
  - Changes are applied one at a time per session, each confirmed before the next.
  - **During a turn** (`capabilities.settingsApply: "nextTurn"`): Codex fixes a turn's settings
    when it starts, so a change made while a turn runs (in Tether or in Codex's TUI) counts from the
    next turn. The header says so: "Mode Read only from the next turn", and under it "This turn
    still runs with Mode Auto." with **Stop this turn** when the turn has more access than shown
    (compared by approval policy and by sandbox, so it works for any combination, not just the
    presets). The driver reports the turn's own settings: those it had when the turn started, or,
    joining a turn already running (a runner restart, a session opened while another client's turn
    runs), the turn's `turn_context` in the rollout. Subagents started in the turn keep its settings,
    so the note and Stop stay while any still runs, and Stop stops them too. It goes back to plain
    "Read only" when nothing runs on the old settings. Policy steps see the running turn's mode.
    Claude Code applies changes to the running turn, so none of this shows there.
  - **A stored session whose thread is running another client's turn** (Codex's TUI in your own
    terminal): Send joins the thread, finds the turn, and is refused as "Codex is still working on a
    turn started elsewhere. Stop it first, or wait for it to finish." The session shows that turn
    running, with its own settings beside yours, and Stop. Nothing is slipped into it.
  - "Default" is remembered: a session on Default still shows Default after a restart or once
    stored, while the thread runs the default model.
  - Changes made in Codex's TUI afterwards show in the header and stay. The settings Codex last
    confirmed are remembered (`<config dir>/codex-threads.json`), so a change with no turn after it
    still shows once the session is stored, though the rollout doesn't have it yet.
  - The rollback is generic (the core's `setting()`): a Claude setting the SDK rejects is rolled
    back too. While Claude's TUI drives in a handoff terminal, the header's settings are disabled
    ("Claude Code's terminal is driving. Change it there.") and the runner refuses them, since the
    TUI takes no settings from Tether. In Codex's shared terminal they keep working: the daemon
    applies them to the thread the TUI shows.
- **Discovery** of Codex threads runs at most once a minute (`thread/list` can take 10–20 s on a
  big store), one call at a time; a folder's list opened in the dialog is fresh to a few seconds.

## Setup

An isolated dev stack with its own ports, config and tmux socket:

```sh
D=/home/ubuntu/tether-scratch/p4
mkdir -p $D/projects/scratch && echo '{"runnerId":"tether-dev-p4","name":"tether-dev-p4"}' > $D/runner.json
cd $D/projects/scratch && git init -q && echo '# Scratch' > README.md && echo 'hello from notes' > notes.txt && git add . && git commit -qm init
# server on :8793
cd server && env -u FOLIATION_ISSUER -u PORT -u TETHER_URL -u TETHER_TOKEN PORT=8793 bun src/index.ts
# runner, with its own tmux socket
cd runner && env -u TETHER_URL -u TETHER_TOKEN TETHER_DEV=1 TETHER_URL=http://localhost:8793 TETHER_TOKEN=dev \
  TETHER_CONFIG_DIR=$D TETHER_TMUX_SOCKET=tether-dev-p4 bun src/index.ts
# web on :5183
cd web && TETHER_SERVER=http://127.0.0.1:8793 VITE_PORT=5183 bunx vite
```

**Folder trust.** Codex's daemon writes `trust_level = "trusted"` for a git repository into
`~/.codex/config.toml` when `thread/start` asks for a writable sandbox there (workspace-write or
danger-full-access; not read-only, no sandbox at all, or a folder outside git; seen on 0.166, on a
throwaway `CODEX_HOME`). So Tether always starts a thread read-only and applies the mode you chose
right after with `thread/settings/update`, confirmed before anything runs (`turn/start` then pins
it): neither writes to the config, and the mode holds. A new session must add nothing to that file.
A folder that isn't trusted doesn't get Codex's project-level config, as for any untrusted folder.

Codex's TUI is the other way in, and Tether can't stop it: in a git repository `config.toml` doesn't
trust, `codex resume --remote` asks whether to trust the folder a moment after its prompt is drawn
(seen with TUI 0.164 on daemon 0.166), and answering yes writes the same entry through the daemon
(`config/batchWrite`). That's the person's own decision in Codex's own screen, so Tether doesn't
answer it or override it. Choose No or quit unless you mean it. Enter says yes, so in these checks
read the screen before typing. `scripts/e2e-p4.mjs` sends no key to the TUI unless the scratch
folder is already trusted: without that its TUI steps stop, and trusting the folder is up to you.

The Codex daemon must be running (`codex app-server daemon version` says `"status":"running"`).
Open http://127.0.0.1:5183. Unless a check says otherwise, use a Codex session in the scratch
folder made with **New session → Codex**, Model **GPT-6-Luna** (the cheapest the daemon lists),
Permissions **Ask first**, then Effort **Low** in the header before the first message.

Look at tmux with `tmux -L tether-dev-p4 ls` (TUIs are `t-codex-<thread id>`) and
`tmux -L tether-dev-p4 capture-pane -p -t =<name>:`. When done: `tmux -L tether-dev-p4 kill-server`.

Automated parts:
- `for p in shared server runner web; do (cd $p && bun test && bunx tsc -p .); done`.
  `runner/src/adapters/codex/*.test.ts`: the WebSocket client against a real Bun server on a Unix
  socket (`ws.test.ts`); recorded daemon streams replayed through the stream (`stream.test.ts`:
  an approval resolved by another connection plus a steer from it, subagents on 0.165 and 0.162,
  live and stored transcripts equal message for message); the driver against a scripted daemon
  (`driver.test.ts`: resume settings, resolved-elsewhere with no answer sent, approve, deny with a
  reason steered in, send/steer/interrupt/settings, subagent stop and messages, a new thread made
  first, a dropped connection, settings applied after the join and confirmed, live changes
  rejected or already in place, remembered settings for a stored header); requests, items and
  modes. `runner/src/core/capabilities.test.ts`: the core following each capability flag,
  including a live setting that's rejected, times out, isn't confirmed or is confirmed late, and a
  send on a harness that doesn't pin (it re-applies a pending setting first).
- `scripts/check-codex-folder-trust.sh`: a private app-server of the daemon's version (own
  `CODEX_HOME`, own socket; the user's daemon and config are never touched, no sign-in needed): new
  sessions in a git repository add nothing to its `config.toml`, and a control that a writable
  `thread/start` does. `node scripts/e2e-p4.mjs` runs it as the step `folderTrust`.
- `node scripts/e2e-p4.mjs`: Playwright at 1280 and 375 px against the real daemon (GPT-6-Luna,
  Low). Playwright comes from `PLAYWRIGHT` (default
  `/home/ubuntu/foliation/web/site/node_modules/playwright/index.mjs`). Set `SCRATCH` to the
  scratch folder above (the script's default is `~/.local/share/tether-dev-p4/projects/scratch`),
  and `BASE`, `RUNNER`, `TMUX_SOCKET`, `RESTART_RUNNER` as its header says. Steps: new, stream,
  approve, deny, steer, midturn, terminal, tuiApprove, tetherApprove, phone, subagent, restart,
  quit, fresh, settings, storedInject, restartMid, subOutlive, subNewTurn, subRestart, subKill9
  (needs `KILL9_RUNNER`), reviewerAuto, netRoots, bgStop, bgNote, nestedStop, tuiPermissions,
  claudeShiftTab (needs `CLAUDE_SCRATCH`, a folder Claude already trusts), subMessage,
  startConfirmed, bgStored, tuiReadOnly (G7b), tuiSteer (D4), tuiAnswerAway (C8b, needs
  `STOP_RUNNER`, `START_RUNNER`), folderTrust, stored.

## Known gaps

- A command in a background terminal is told apart only by the turn that started it: Codex offers no
  way to change its settings, so Stop the command is the only way to tighten it. Tether looks for
  such commands when settings change (on a stored session too: a mode change asks the daemon, without
  joining, and joins only if one is up), a turn ends and on joining, then every 5 s only while one has
  more access than shown; one started by another client between those is noticed at that turn's end.

- Settings remembered as confirmed (B5c) are what Tether saw. If the daemon restarts before the
  thread's next turn, it reloads the thread from its rollout and may run with the older settings
  there; the stored header shows the remembered ones until Tether joins the thread again, when it
  shows (and keeps) what the thread really has.

- A thread made by "Start in the terminal" needs a name before Codex's TUI can join it (an empty
  thread can't be resumed by another client, and only `thread/name/set` writes it). Tether names it
  "New session" and, after its first turn, after its first message; Codex can't clear a name, so
  its own auto-title doesn't run on such a thread.
- Codex 0.165 sends a subagent's task to it encrypted (the `spawn_agent` call's message), so a
  subagent's view can't show the task it was given; its card shows the task's name.
- In **Ask first** (untrusted), Codex 0.165 fails a subagent's approval requests at once (the daemon
  resolves them itself within a millisecond; a probe resuming the child thread gets "list_turns is
  not supported yet"). Tether shows the card for an instant and closes it as resolved elsewhere;
  the subagent reports the command was rejected. Use Auto for subagents that run commands.
- `codex resume` won't take `-a untrusted` (the CLI only accepts on-request and never), so with Ask
  first the TUI is launched without `-a`/`-s` and keeps the thread's own settings.
- A message steered in (from Tether or the TUI) while a command runs, and a command left running in
  the background past its turn, are shown live where they started, but the store orders items by
  completion. That's inherent (live items arrive by start); when the session later goes stored that
  part of the transcript is redrawn in the store's order (one reset).
- A tool call denied or stopped before it ran has a card live, but the store has no item for it, so
  the card goes when the session is stored (or reopened).
- A message to a subagent counts as delivered on the main agent's next message to that subagent:
  Codex doesn't say what was sent, so one the main agent sent on its own would count too.
- Codex's plan updates (`turn/plan/updated`) aren't shown: they aren't in the store, so stored and
  live would differ.
- MCP forms and links (elicitations other than tool approvals) can only be answered in Codex's TUI (J6).
