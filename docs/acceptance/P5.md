# P5 acceptance: daily-driver features

Manual checks for P5: steering and the message queue (SPEC §9), Claude subagents steered through the
main agent (§6a), attachments, Web Push notifications, and Home's inbox (§10). Each check gives exact
steps and the expected result. "Desktop" means a browser window at least 1024 px wide; "phone" a real
phone, or a browser at 375 × 812 with touch emulation. "Two devices" means two browsers (or a browser
and a phone) on the same app at once.

Phase acceptance (SPEC §11):
- Steer and queue work on both harnesses, two devices stay in sync, and the queue survives a restart
  and a terminal handoff (A–D).
- An attachment from the phone reaches each harness (E).
- Push arrives for a request, a finish and a failure, and deep-links (F).
- The inbox is correct and read state syncs (G).
- Claude subagent steering via the parent lands in the subagent (H).

`scripts/e2e-p5.mjs` runs most of these headless against real Claude (Haiku) and Codex (the
cheapest model, Low effort); each check below names its step. What needs a real phone is marked
**Phone only**.

## How it works

- **Composer keys (desktop).** Enter: send when idle, **steer** into the running turn when the
  harness can (both can), else queue. **Tab** (with text): queue. **⌘/Ctrl+Enter**: stop the turn and
  send now. Shift+Enter: newline. **Esc** on an empty box: stop. On phones Enter is a newline; the
  button sends (Send, Steer or Queue) and the ⌄ menu beside it has *Queue for after this turn*, *Stop
  and send now* and *Stop*.
- **Steer.** Codex: `turn/steer` into the running turn. Claude: the message goes into the running
  query's streaming input, and Claude Code takes it at its next step (stored as a queued command, so
  the stored transcript shows it in the same place). A steer can't be taken back.
- **Queue.** Held on the runner, in `runner.json` (written at once), so every device sees the same
  list and it survives a restart. One message per turn. Each waiting message can be edited (✎), moved
  up (↑) or cancelled (×) from any device. The queue **waits** (held, with a reason and *Resume*):
  after **Stop** (released when you send something or press Resume), after a **failed turn**, after a
  turn **cut off by a runner restart**, and while the **terminal drives** a handed-off Claude session
  (released by Back to Tether; if the TUI exits by itself the hold becomes "paused" and waits for you).
- **Subagents.** Codex subagents take messages directly (`turn/steer` on the child thread). Claude
  subagents (`steer: "via-parent"`): the message box in a running subagent's view asks the main
  agent, as Tether ("From Tether, on your behalf"), to call its `SendMessage` tool to that subagent
  with your exact text. The subagent's view shows your message with "Sending via the main agent…",
  then "Sent via the main agent" once the main agent's `SendMessage` call to it is seen, or "Not
  delivered" if the main agent's turn ends without one.
- **Attachments.** Paste, drop, 📎 (any file) or 📷 (phones: the camera). Photos are scaled to 2048 px
  on the long edge in the browser; images up to 10 MB, other files up to 25 MB, at most 10 per
  message (`shared/limits.ts`). Files upload in 256 KB chunks over rpc and are kept, read-only, under
  `<config dir>/attachments/<session>/`. The message ends with an "Attached files:" block listing
  each path (the transcript shows it as chips); PNG/JPEG/GIF/WebP also go to the harness as images
  (Claude: image blocks; Codex: `localImage` inputs). A message may only name files of its own session
  (a subagent: its main session's too).
- **Push.** The server keeps the app's VAPID key pair (`TETHER_VAPID_PUBLIC_KEY`,
  `TETHER_VAPID_PRIVATE_KEY`, optional `TETHER_PUSH_SUBJECT`; a dev server makes a pair per process)
  and hands the public key to browsers and the pair to runners. A device turns notifications on once
  (Home → Notifications on this device → Turn on); it subscribes with the app's key and every
  connected runner stores the subscription (`<config dir>/modules/push/push.json`). Runners send:
  **Needs you** (a request; Claude's TUI asking in the terminal), **finished** (with the start of the
  last reply), **failed** (with the error). A device that is looking at that session (its page visible
  on it, or on one of its subagents) is skipped. A click opens the session (in the open Tether window
  if there is one).
- **Home** is the landing page: one ranked inbox across runners: **Needs you** (open requests, a TUI
  asking), then **Failed** and **Finished** turns nobody has looked at, then **Working**. Read state
  is on the runner, so it is the same on every device: opening the session anywhere marks it read
  (presence), and so does ✓ (Mark read) or *Mark all read*. A turn you stopped yourself, or one that
  ended while someone was looking, never shows as unread.

## Setup

An isolated dev stack with its own ports, config and tmux socket:

```sh
D=~/.local/share/tdp5
mkdir -p $D/projects/scratch && echo '{"runnerId":"tdp5","name":"tdp5"}' > $D/runner.json
cd $D/projects/scratch && git init -q && echo '# Scratch' > README.md && git add . && git commit -qm init
# server on :8794 (dev mode makes push keys for this process)
cd server && env -u FOLIATION_ISSUER -u PORT -u TETHER_URL -u TETHER_TOKEN PORT=8794 bun src/index.ts
# runner
cd runner && env -u TETHER_URL -u TETHER_TOKEN TETHER_DEV=1 TETHER_URL=http://localhost:8794 TETHER_TOKEN=dev \
  TETHER_CONFIG_DIR=$D TETHER_TMUX_SOCKET=tdp5 bun src/index.ts
# web on :5184
cd web && TETHER_SERVER=http://127.0.0.1:8794 VITE_PORT=5184 bunx vite
# end to end (RESTART_RUNNER restarts the dev runner for the restart step)
PLAYWRIGHT=/home/ubuntu/foliation/web/site/node_modules/playwright/index.mjs RESTART_RUNNER='…' node scripts/e2e-p5.mjs
```

Open http://127.0.0.1:5184. Unless a check says otherwise use a **Claude** session made with New
session → Claude Code, Model **Haiku**, in the scratch folder, Permissions **Bypass permissions** (so
the slow test prompts don't ask), and a **Codex** session with Model **GPT-6-Luna**, Effort **Low**.
A "slow prompt" is: `Use the Bash tool to run exactly: sleep 20   Then reply with exactly one word: DONE`.

A phone needs the app over https to use notifications and the camera (production, or a tunnel);
everything else works on the dev stack at 375 px.

## A. Steer (`steer`, `codex`)

A1. **Claude, desktop.** Send a slow prompt. While it runs the placeholder says "Claude is working…
(Enter to steer, Tab to queue)" and, with text typed, the button is **Steer** with a ⌄ menu. Type
"After that, also reply with the word PINEAPPLE." and press Enter.
→ The message shows at once as your bubble (on every open device). When the turn ends, Claude's
reply includes PINEAPPLE. Reload: the stored transcript shows the steer in the same place.

A2. **Codex, desktop.** Same with "When you reply, also include the word PINEAPPLE."
→ The bubble shows; Codex's reply includes PINEAPPLE.

A3. **Phone.** Running turn; type text; tap **Steer**.
→ As A1. Enter on the phone keyboard only adds a newline.

A4. **Nothing running.** `steer` op on an idle session (e.g. `rpc("steer")` from the console).
→ "Nothing is running to steer. Send it as a new message instead."

A5. **Two devices.** Steer from the phone while the desktop watches.
→ The desktop shows the bubble within a second and both transcripts are identical after the turn.

## B. The queue (`queue`, `stopSend`, `codex`)

B1. **Queue with Tab.** Desktop, slow prompt running. Type "Reply with exactly: QUEUED-ONE", press
Tab.
→ The box clears; above the composer "1 message waits for this turn to end." with the message,
↑ (not on the first), ✎ and ×. The phone shows the same list within a second.

B2. **Queue from the phone menu.** Phone: type "Reply with exactly: QUEUED-TWO", tap ⌄ → *Queue for
after this turn*.
→ It joins the end of the list on both devices.

B3. **Edit, move, cancel from either device.** Phone ✎ on QUEUED-TWO → change to QUEUED-2B → Save
(or Enter). Desktop ↑ on it. Queue a third and × it on the phone.
→ Every change shows on the other device within a second; the cancelled one is gone everywhere.
Emptying a message's text in ✎ cancels it.

B4. **One per turn, in order.** Let the turn end.
→ QUEUED-2B goes out as the next turn (its bubble appears, the list shrinks), then QUEUED-ONE after
that turn. The cancelled one never goes out.

B5. **Idle queue.** On an idle session press Tab with text.
→ It goes out at once (nothing to wait for).

B6. **Stop and send now.** Slow prompt running, one message queued. Type "Reply with exactly: NOW",
press ⌘/Ctrl+Enter (phone: ⌄ → *Stop and send now*).
→ The turn stops ("Interrupted"), NOW goes out at once, and the queued message follows after NOW's
turn.

B7. **Stop holds the queue.** Slow prompt running, one message queued. Esc on the empty box (or Stop).
→ The turn stops; the list says "Paused after Stop. Send something, or resume." with **Resume**.
Nothing goes out. Resume → the queued message goes out. (Sending any message also releases it: the
queue goes on after that message's turn.)

B8. **Failed turn holds it.** In a session created with a model that doesn't exist (console:
`rpc("newSession", {harness: "claude", projectPath: "<scratch>", model: "claude-no-such-model-1"})`;
switching a live session's model to a bad one is ignored by Claude Code), send something and queue a
message while it runs.
→ The turn fails ("There's an issue with the selected model…"); the queue says "Paused after a
failed turn." A harness process that dies mid-turn counts the same.

B9. **No steer harness.** (Not reachable with the two core harnesses; covered by unit tests:
`composerKeys.test.ts`, and the core queue tests.) Enter while running would queue.

B10. **Limits.** Queue 50 messages, then one more.
→ "At most 50 messages can wait. Send or cancel some first."

B11. **Subagents** have no queue: their composer only sends into the subagent (H, and P4 for Codex).

## C. The queue across a terminal handoff (`terminal`)

C1. Claude, slow prompt running, one message queued. Press **Terminal**.
→ Inline: "Stop this turn and open the terminal? 1 queued message will wait until you're back." with
**Stop and open terminal** / **Keep working**.

C2. Stop and open terminal.
→ The TUI opens; the list says "Waiting until you're back from the terminal." (no Resume). Nothing
is typed into the TUI.

C3. Queue another message while the TUI drives (Tab in the composer).
→ It joins the held list (Enter in terminal mode still types into the TUI).

C4. Close the panel → **Back to Tether**.
→ The session goes live; the held messages go out one per turn.

C5. Instead of Back to Tether, `/exit` in the TUI.
→ The session goes stored; the list says "Paused after Stop…": your next message (or Resume) releases it.

C6. **Codex** (shared terminal): the queue isn't held while its TUI is open; messages typed in the TUI
end turns like any other, and the queue goes on after them.

## D. The queue across a runner restart (`restart`)

D1. Claude, slow prompt running, one message queued. Restart the runner (Ctrl-C, start again).
→ After it reconnects the session shows "This turn stopped because the runner restarted…", and the
queue is back, held: "Paused: the runner restarted mid-turn." with Resume (on every device).

D2. Resume (phone).
→ The queued message goes out.

D3. Queue on an idle-but-held session, stop the runner, start it.
→ Still there, in the same order, same hold.

D4. **Codex** (persistent): slow prompt, queue one, restart the runner.
→ The turn goes on in the daemon; the runner rejoins it; when it ends the queued message goes out
without Resume.

D5. `runner.json` has the session's `queue` (and `queueHeldBy`) while anything waits, and neither
once the queue is empty.

## E. Attachments (`attach`)

E1. **Phone camera → Claude.** Phone: 📷, take a photo of something red (or pick one). 📎, pick a
text file containing "The secret word is MANGO." Ask: "What color is the attached image, and what is
the secret word in the attached text file?"
→ Chips with thumbnails/size and upload % then size; Send is disabled until both finish. Claude
answers red and MANGO. Your message shows the image and a 📎 secret.txt chip (no path text).

E2. **Same to Codex.**
→ Codex answers red and MANGO; the image shows in the transcript (read back from the attachments
folder), the file as a chip.

E3. **Desktop paste and drop.** Paste a screenshot (⌘V) into the box; drag a file onto the composer
(it outlines while dragging).
→ Each becomes a chip; sending works as E1.

E4. **Remove before sending**: × on a chip.
→ It's gone and isn't sent.

E5. **Limits.** A 30 MB zip → chip shows "Failed" ("Too large (30.0 MB): files can be up to 25.0
MB."). An 11th file → "At most 10 files on one message." A 12 MP photo uploads as a ≈2048 px JPEG.

E6. **Queued with attachments.** Running turn: attach a file, Tab.
→ The queued row shows "· secret.txt"; when it goes out, the harness gets the file.

E7. **Steer with an attachment** (Claude and Codex): attach an image, Enter while running.
→ It reaches the running turn.

E8. **Where they live**: `ls $D/attachments/` shows one folder per session, files `<8 hex>-<name>`,
mode `-r--------`. A message naming another session's file (console rpc) → "That attachment doesn't
belong to this session."

E9. **Reload / other device**: the transcript shows the image and chips the same (read from the
harness's store).

E10. **Terminal mode** (Claude TUI driving): attach a file and send → the TUI gets your text plus the
"Attached files:" block with the path.

## F. Push notifications (`push`)

F1. **Turn on (desktop Chrome or Firefox, https or localhost).** Home → Notifications on this device
→ Turn on → allow.
→ "This device gets a notification when a session needs you, finishes or fails…" with Test and Turn
off. Test → a "Tether notifications work" notification.

F2. **Request.** Close or hide the Tether tab. In a session in Ask first, from the phone, ask for a
Bash command.
→ "Needs you · <title>" "Claude wants to run …" on the desktop. Click → Tether opens (or focuses)
on that session with the request in the dock.

F3. **Finished.** Hide the tab, let a turn finish.
→ "<title>" with the start of Claude's reply. Click opens the session; it's no longer unread.

F4. **Failed.** A session on a bad model (B8), hide the tab, send.
→ "Failed · <title>" "Claude's turn failed: …".

F5. **No duplicate for the device looking at it.** Keep the session open and visible on the desktop
while it finishes.
→ No notification on the desktop (other devices still get one). Switch to another tab first → it
notifies.

F6. **Several runners.** With a second runner connected, a session on it notifies the same device
(one subscription, every runner told).

F7. **Turn off** → no more notifications; the runners drop the subscription (`push.json`).

F8. **Gone subscriptions** (browser data cleared): the push service answers 410 and the runner drops
it (unit test).

F9. **Phone only** (iPhone: add Tether to the Home Screen first, iOS 16.4+; Android Chrome works in
the browser): F1–F5 on the phone; tapping a notification opens the app on the session. Not verifiable
headless: the real browser push services (FCM, Apple, Mozilla), the permission prompt, and a click on
a real notification.

F10. **No keys on the server** (production without TETHER_VAPID_*): Home says "Notifications aren't set
up on this server yet…" and nothing else changes.

Headless (`push` step): a subscription pointing at a local push service gets a VAPID-signed test,
request, finished and failed push that decrypt with the device's keys; a device id looking at the
session (presence) gets nothing until it looks away; the service worker handles a push delivered
through DevTools (`ServiceWorker.deliverPushMessage`) and its click handler opens the session in the
open window. Headless Chromium never grants notification permission to a service worker, so the
step records `showNotification`'s arguments instead of showing one, and dispatches the click itself;
the real permission prompt, `PushManager.subscribe` against a real push service, and a click on a
real notification need a real browser (F1–F5, F9).

## G. Home's inbox (`inbox`, `home`)

G1. Open the app at `/` on desktop and phone.
→ Home: the inbox ("Nothing needs you…" when empty), then Runners and Notifications. No sideways
scrolling at 375 px.

G2. **Finished, unread.** With nobody looking at a session (be on Home), let a turn finish (start it
from the phone and go Home there too).
→ A **Finished** row (title, glyph, folder, time) on both devices within a second. The sidebar row is
bold with "· Finished".

G3. **Read state syncs.** Open that session on the phone.
→ The desktop's Finished row disappears (and the bold) within a second.

G4. **Failed.** B8 with nobody looking.
→ A **Failed** row with the error under it, on both devices. ✓ on the desktop → gone on the phone.

G5. **Needs you** rows come first (open requests, oldest waiting first; a TUI asking in the
terminal), then Failed, Finished, then **Working** (running turns). A subagent's request counts in
its parent's row. Rows across several runners are mixed by rank (runner name shown when >1 online).

G6. **Mark all read** (shows with 2+ unread) clears every Finished/Failed row everywhere.

G7. **Looking while it ends.** Keep a session open while its turn ends → it never becomes unread.
Stop a turn yourself → not unread either.

G8. **Restart**: unread state is in `runner.json`; after a runner restart the rows come back the same.

G9. Starting a new turn in an unread session clears its unread mark (it's Working instead).

## H. Claude subagents steered via the main agent (`relay`)

H1. In a Claude session ask: Use the Agent tool with run_in_background set to true, subagent_type
"general-purpose", description "Waiting helper", and the prompt "Run the Bash command sleep 45. Then
reply with every message you received from the main agent while you waited, word for word." Then
wait for it and tell me exactly what it replied.

H2. Open the running subagent (its card's link, or the sidebar row under the session).
→ The composer says "The subagent is working… (Enter to send it a message)" (Stop stops just it).

H3. Type "The code word is KUMQUAT." and press Enter.
→ It shows in the subagent's view as your bubble with "Sending via the main agent…". In the main
session a "From Tether, on your behalf" message asks the main agent to pass it on; the main agent's
`SendMessage` card appears; the subagent's bubble then says **Sent via the main agent**.

H4. When the subagent finishes, its reply (and the main agent's summary) contains KUMQUAT.

H5. **Not delivered.** If the main agent ends its turn without calling SendMessage for it, the
bubble says "Not delivered: the main agent didn't pass it on." (unit test; hard to provoke on Haiku).

H6. A finished subagent: its view has no composer ("A subagent's transcript…"); the `steer` op says
"This subagent has finished. Message the main session instead."

H7. **Codex** subagents keep P4's direct steer (`turn/steer` on the child thread); the bubble is the
subagent's own user message (no relay marks).

## I. Reconnects and errors

I1. Phone sleeps with messages queued; another device edits the queue; wake the phone.
→ It resubscribes and shows the current queue.

I2. Upload interrupted (turn off Wi-Fi mid-upload): the chip shows Failed with the error; × and attach
again. Partial uploads are dropped by the runner after 10 minutes.

I3. Runner offline: the composer says "The runner is offline."; queue ops fail with "That runner is
offline." and nothing is lost.

I4. Server redeploy: browsers and runners reconnect; presence is sent again on every connect, runners
get the viewers again; queues, read state and subscriptions are on the runner and unaffected. (In
dev the push key changes with each server start, so a subscribed browser subscribes again on its next
connect.)
