# P0 acceptance: skeleton

Manual checks for the skeleton: the relay, the runner connection, the web shell and its runner
list. Every check has exact steps and the expected result. "Desktop" is a laptop browser window
at least 1024 px wide; "phone" is a real phone or a browser at 375 × 812 with touch emulation.

Phase acceptance (SPEC §11): the runner shows as connected in the browser, the server redeploys
without the runner noticing, and a reconnect works. Sections A–C cover that; the rest cover
everything around it.

## Setup

### Local (dev mode)

Use the isolated dev stack, never the production runner or `~/.config/tether`.

```sh
mkdir -p ~/.local/share/tether-dev && echo '{"runnerId":"tether-dev","name":"tether-dev"}' > ~/.local/share/tether-dev/runner.json
# terminal 1: server on :8790
cd server && env -u FOLIATION_ISSUER -u PORT bun src/index.ts
# terminal 2: runner
cd runner && TETHER_URL=http://localhost:8790 TETHER_TOKEN=dev TETHER_CONFIG_DIR=~/.local/share/tether-dev bun src/index.ts
# terminal 3: web on :5180
cd web && bunx vite
```

Open http://127.0.0.1:5180. To reach it from a phone, tunnel the port (for example
`ssh -L 5180:127.0.0.1:5180 host`) or use the production setup below.

### Production (Foliation)

The app `tether` deployed from `main`; a runner on a machine with `TETHER_URL` set to the app's
URL and `TETHER_TOKEN` a runner service token. Sign in to Foliation as the app's owner.

### Terms

- **Connected row:** the runner's row in the main area shows a green dot, "Connected", and below
  it the hostname (when it differs from the runner id) and each harness with its version, e.g.
  "Claude Code 2.1.312 · Codex 0.164.0".
- **Disconnected row:** grey dot, "Disconnected · last seen <time>", and an × (Forget) button.
- **Reconnecting banner:** a red banner across the top, "Reconnecting…" ("Offline ·
  reconnecting…" when the device reports no network).

## A. First connection

| # | Steps | Expected |
|---|---|---|
| A1 | Start the server, then the runner. | Runner log: `Tether runner 0.2.0: tether-dev, config in …`, `harnesses: claude <v>, codex <v>`, `connected to http://localhost:8790 as tether-dev`. Server log: `runner tether-dev connected (<hostname>; claude <v>, codex <v>)`. |
| A2 | Desktop: open the app. | Sidebar: "Tether" heading, Home (selected), a "Runners" section with `tether-dev` and a green dot, and your name at the bottom ("Developer" in dev mode). Main area: heading "Runners" and a connected row for `tether-dev`. No banner. |
| A3 | Compare the versions in the row with `claude --version` and `codex --version` on the runner machine. | They match. A harness that isn't installed is left out; with neither installed the row says "No harnesses found". |
| A4 | Hover the green dot (desktop). | Tooltip "Connected". |
| A5 | Click **Ping**. | Within a second the status line reads "Connected · Answered in N ms". |
| A6 | Phone: open the app. | Header bar with "Tether" and a menu button; the main area shows the connected row. No horizontal scrolling anywhere; the harness line truncates with "…" rather than overflowing. |
| A7 | Phone: tap the menu button. | A drawer slides in with Home, Runners → `tether-dev` with a green dot, and your name. Tapping Home or the runner closes it; so do Escape and tapping outside. |
| A8 | Phone: tap **Ping**. | Same as A5. The button is comfortably tappable. |
| A9 | Start the web app before any runner has ever connected (fresh browser profile or cleared site data, no runner running). | Main area: "No runner has connected yet", with a line about starting the runner with `TETHER_URL` and `TETHER_TOKEN`. The sidebar has no Runners section. |
| A10 | With the A9 page open, start the runner. | Without reloading, the empty state is replaced by a connected row, and the sidebar gains the Runners section. |

## B. Runner restarts and drops

| # | Steps | Expected |
|---|---|---|
| B1 | With desktop and phone both open, stop the runner with Ctrl-C. | Within a second, on both devices: grey dot, "Disconnected · last seen just now", an × button instead of Ping. Server log: `runner tether-dev disconnected`. |
| B2 | Kill the runner hard (`kill -9 <pid>`). | Same as B1 (the TCP connection closes with the process). |
| B3 | Start the runner again. | Both devices show the connected row again within about a second, no reload. Ping works. |
| B4 | Ping on desktop, then restart the runner. | After the restart, the status line is plain "Connected": the old "Answered in …" result is gone. |
| B5 | Leave the runner stopped for over a minute. | "last seen" counts up ("1 min ago", "2 min ago" …) without reloading. |
| B6 | Start a second runner with the **same** config directory (same `runnerId`) while the first is running. | The newcomer takes over: the browser shows exactly one row, connected. The first runner logs `another runner connected with this runner's id (…). Each runner needs its own runnerId in runner.json. Retrying in 60s.` and waits 60 s before trying again, so the two never flap every second. Stop the extra copy; within about a minute the first is connected again. |
| B7 | Network drop on the runner: block the runner's traffic to the server without closing the socket, e.g. `sudo iptables -A OUTPUT -p tcp --dport 8790 -j DROP` (dev) — then remove the rule. | Within about 60–80 s the runner logs `no word from the server in …s; reconnecting` and keeps retrying with growing delays (`retrying in 1.0s`, `2.0s` … at most 30 s). The server notices the dead socket on its own (within about 2 minutes) and the browser then shows the runner disconnected. After removing the rule the runner reconnects at its next retry and the browser shows it connected. |
| B8 | Runner machine sleeps (laptop lid) for a few minutes, then wakes. | While asleep: disconnected in the browser (after the server's idle timeout). After waking: connected again within about 30 s, no manual restart. |

## C. Server restarts and redeploys

| # | Steps | Expected |
|---|---|---|
| C1 | With desktop and phone open and the runner connected, stop the server. | Both devices show the Reconnecting banner within a second; the runner row shows a grey dot and "Waiting for the server", with no Ping or × button. Runner log: `disconnected (1006 …)`, then `retrying in …` lines. |
| C2 | Start the server again. | The banner disappears on both devices; the row returns to connected (the runner reconnects in its next retry, at most a few seconds when the outage was short). Ping works. |
| C3 | Keep the server down for 2 minutes, then start it. | The runner's retry delay is capped at 30 s, the browser's at 15 s; both are connected again within 30 s of the server starting. |
| C4 | Production: redeploy the app (push to `main` or redeploy from Foliation) while a browser is open and the runner is connected. | The banner may flash during the switch. Afterwards the runner is connected again without being restarted (`systemctl --user status` shows no restart; its log shows a `disconnected` / `connected` pair only). The runner process ID is unchanged. |
| C5 | Production: deploy with a protocol version change (`PROTOCOL_VERSION` bumped) while a runner on the old version runs. | Open pages show an info banner "Tether was updated." with **Reload**; reloading clears it. The old runner is refused: its log says `the server refused this runner: protocol mismatch: the app speaks N, the runner M; update the runner. Retrying in 300s.`, and it shows as disconnected until it's updated. |

## D. Browser reconnects

| # | Steps | Expected |
|---|---|---|
| D1 | Desktop: turn Wi-Fi off for 10 s, then on. | The banner shows "Offline · reconnecting…" while offline (once the socket notices), and disappears within a couple of seconds of the network returning: the browser reconnects as soon as the device reports it's online, without waiting for its backoff. |
| D2 | Phone: lock the phone for 5 minutes with the app open, then unlock. | Within a few seconds of unlocking the page shows the current state (connected row). If the socket died while asleep, the Reconnecting banner shows briefly and clears. |
| D3 | Phone: switch from Wi-Fi to mobile data with the app open. | Reconnects within about 5 s of the page being visible; no reload needed. |
| D4 | Desktop: put the tab in the background for 10 minutes, then return. | The page is current when you return (a dead socket is detected within 5 s of the tab becoming visible). |
| D5 | Reload the page while the runner is stopped. | The runner still appears, as disconnected with its last-seen time: the browser remembers runners it has seen. |
| D6 | With the runner stopped and shown disconnected, click × (Forget). | The row disappears at once, no confirmation; it stays gone after a reload. Starting the runner brings it back. |
| D7 | Server stopped, page reloaded. | No banner (the page never connected), the remembered runners show "Waiting for the server". Starting the server connects without reloading. |

## G. Authentication

| # | Steps | Expected |
|---|---|---|
| G1 | Dev: start a runner with `TETHER_TOKEN=wrong`. | Runner log: `the server refused TETHER_TOKEN (403): check the token and that it's a runner service token`, repeated with growing delays (up to 30 s). It never appears in the browser. |
| G2 | Dev: start a runner with `TETHER_URL` pointing at a port with nothing listening. | Runner log: `can't reach http://…/api/runner: …` with growing delays; it connects by itself once the server is started there. |
| G3 | Production: open the app in a private window, signed out of Foliation. | Foliation's sign-in page, not Tether. |
| G4 | Production: open the app signed in as someone the app is shared with who isn't an owner. | "This Tether belongs to someone else" with a line saying only owners can use it. No runner data is shown. `/api/ws` answers 403. |
| G5 | Production: with the app open, sign out of Foliation in another tab, then make the page reconnect (stop and start the network). | "Sign in to use Tether" with a **Reload** button; Reload leads to sign-in. |
| G6 | Production: a runner with a revoked service token. | Same log as G1; the browser shows it disconnected once its existing connection ends. |
| G7 | Production: a service token whose name isn't `runner` / `runner-*`, or whose role isn't editor. | Refused (G1 log). |
| G9 | Dev: from a page on another origin (e.g. open the browser console on any other site) run `new WebSocket("ws://127.0.0.1:5180/api/ws")`. | Refused (the server answers 403 "cross-origin socket refused"); the dev server's own page still connects. |
| G11 | Dev: `curl -H 'Host: evil.example' http://127.0.0.1:8790/api/me` | 403 "dev mode answers only localhost" (a DNS-rebinding page can't become the owner). `/api/health` still answers. |
| G12 | Start the runner with neither `TETHER_URL` nor `TETHER_TOKEN` set (and no `TETHER_DEV`). | It exits at once: `Set TETHER_URL and TETHER_TOKEN (the app's URL and a runner service token), or TETHER_DEV=1 for a local dev server.` With `TETHER_DEV=1` it dials `http://localhost:8790` with token `dev`. |
| G10 | Production: start the server with `FOLIATION_ISSUER` set and `FOLIATION_AUDIENCE` unset. | It exits at once with "refusing to start without the audience check". (Foliation always sets both.) |
| G8 | Production: `curl https://<app>/api/health`. | `{"ok":true}` without signing in (Foliation's health check). |

## Automated checks

```sh
for p in shared server runner web; do (cd $p && bun test && bunx tsc -p .); done
```

All pass, `tsc` clean. The relay tests cover subscriptions, terminal routing, runner replacement
and rpc timeouts; the runner tests cover the connection (hello, rpc, reconnect after a server
restart, stale answers dropped, silence detection, refused token), the event bus, ops, config,
harness detection and the PTY.
