# P2 acceptance: requests (approvals and questions)

Manual checks for P2: the request broker, approvals and questions on any device, idempotent
answers, requests that survive a runner restart, subagents' requests, and permission modes. Each
check gives exact steps and the expected result. "Desktop" means a browser window at least 1024 px
wide. "Phone" means a real phone, or a browser at 375 × 812 with touch emulation.

Phase acceptance (SPEC §11):
- In Ask first (`default`) mode, an edit request appears on both devices (A1).
- Answering on the phone clears it on desktop (A2).
- A second answer says "Already answered." (A3, A4).

## Setup

The isolated dev stack from P1.md, with its own ports and config so it can run beside others:

```sh
D=~/.local/share/tether-dev-p2
mkdir -p $D && echo '{"runnerId":"tether-dev-p2","name":"tether-dev-p2"}' > $D/runner.json
mkdir -p $D/projects/scratch && cd $D/projects/scratch && git init -q \
  && printf 'export const add = (a: number, b: number) => a + b;\n' > math.ts \
  && printf '# Scratch\n\nA scratch project for Tether tests.\n' > README.md && git add . && git commit -qm init
# server on :8791
cd server && env -u FOLIATION_ISSUER -u PORT -u TETHER_URL -u TETHER_TOKEN PORT=8791 bun src/index.ts
# runner
cd runner && env -u TETHER_URL -u TETHER_TOKEN TETHER_DEV=1 TETHER_URL=http://localhost:8791 TETHER_TOKEN=dev TETHER_CONFIG_DIR=$D bun src/index.ts
# web on :5181
cd web && TETHER_SERVER=http://127.0.0.1:8791 VITE_PORT=5181 bunx vite
```

Open http://127.0.0.1:5181. Unless a check says otherwise, use a new session in the scratch folder
with **Haiku** and Permissions **Ask first**.

Automated parts:
- `for p in shared server runner web; do (cd $p && bun test && bunx tsc -p .); done`. The broker
  (`runner/src/core/broker.test.ts`), requests in sessions and across a restart on a fake harness
  (`requests.test.ts`), and Claude's prompts as requests (`adapters/claude/requests.test.ts`).
- `node scripts/e2e-p2.mjs`: Playwright at desktop and phone size against real Claude (Haiku). Set
  `BASE`, `RUNNER`, `SCRATCH` and `RESTART_RUNNER` (a command that restarts the dev runner) as its
  header says. Steps: new, approve, deny, question, multi, subagent, restart, plan, planApprove.

### Terms

- **Dock:** the requests area just above the composer. It holds one card per open request and
  never scrolls with the transcript. With many cards (or a long plan) it scrolls inside itself, up
  to about half the screen.
- **Card:** one request. An approval has a title ("Claude wants to write notes.txt"), what the tool
  would do (the command, the diff, the content, or the plan), and **Approve**, **Deny**, **Deny with
  reason**. A question has its options as buttons, a text box, **Send answer** and **Dismiss**.
- **Needs you:** a session with an open request. Its row says "· Needs you" with an amber dot, the
  sidebar's Runners section says "N need you", and Home lists those sessions under their runner.

## A. Approvals on two devices (the phase acceptance)

| # | Steps | Expected |
|---|---|---|
| A1 | Open the session on desktop and on the phone. On desktop send: "Create a file notes.txt containing the word hello, using the Write tool. Do nothing else." | Within a few seconds both devices show a card "Claude wants to write notes.txt" with the full path and the content `hello`. The transcript's **Write** card says "Waiting for you" instead of a spinner, and above the composer reads "Waiting for you below." The header's dot and the row's dot turn amber; the row says "Needs you". The composer says "Waiting for your answer above" and its button is Stop. |
| A2 | On the phone tap **Approve**. | The card disappears on the phone and on desktop at the same time (well under a second). The Write card turns into a check mark, Claude finishes, and `notes.txt` exists with `hello`. "Needs you" goes from the row. |
| A3 | Repeat A1 and note the request id (devtools: the session's `state.requests[0].id` in the store). Approve on the phone, then on desktop answer the same id again from the console: `(await import("/src/connection.ts")).rpc("<runner>", "answerRequest", { sessionId, requestId, allow: true })`. | It rejects with "Already answered.". Claude ran the tool once. (`e2e-p2.mjs approve` does this, and also taps Approve on a card held stale on desktop: the dock says "Already answered." in its place for a few seconds.) |
| A4 | Two devices tap Approve on the same card at the same moment. | One wins. The other device shows "Already answered.". The tool runs once. |
| A5 | Ask for an edit to an existing file ("Change add in math.ts to use a function declaration"). | The card says "Claude wants to edit math.ts" and shows the diff, removed lines red, added green. A long diff scrolls inside the card. |
| A6 | Ask for a command that needs approval ("Run `touch x.txt` with Bash"). | "Claude wants to run a command", with Claude's description of it and the command in monospace. When Claude Code gives a reason for asking ("This command uses shell operators that require approval for safety") it shows under the title. Read-only commands such as `ls` and `pwd` don't ask: Claude Code allows them in Ask first. |
| A7 | Ask Claude to do two things that each need approval in one turn ("Create a.txt and b.txt with Write, in parallel"). | One card per request, oldest first. Answering one leaves the other. |
| A8 | Phone at 375 px: a request with a long command or a long path. | Nothing scrolls sideways. The buttons wrap onto a second line rather than overflowing. The command wraps inside the card. |

## K. Policy steps (for modules; not visible in the core)

The core ships with no policy steps, so every request goes to a person. A step is a function
`(request, { rootSessionId, projectPath, permissionMode }) => allow | deny(reason) | undecided`
with a `source` (`"judge"`, `"rule"`, …) passed to `createRunner({ policy })`. When one decides,
nothing is shown to a person and the transcript gets a notice such as "A rule allowed Claude's
request to run `ls`: ls is harmless" (`requests.test.ts` covers it). A step that throws is skipped.

## Codex (P4)

A request may close without a person answering in Tether: the driver aborts its signal with the
reason `RESOLVED_ELSEWHERE` when the harness says it was answered in its own UI, and the card closes
everywhere (outcome `elsewhere` on the bus). Tested with the fake harness; checked for real in P4.

## Deliberately left for later

- **No eager resume after a restart.** Claude Code doesn't ask again on its own when a session
  is resumed (probed: a resumed session with a pending Write just sits idle). Rather than send a
  message nobody typed at startup, Tether shows the saved request at once and resumes the session
  when you answer it, with a message saying what you decided. When Claude then asks the same tool
  with the same input, the broker matches it to the saved request and keeps its id.
- **"Always allow"** and Claude Code's permission suggestions (add a rule, switch to Accept edits
  for the session) aren't offered: they come back as policy steps.
- **Answering in the terminal** (P3): open requests are cancelled when the TUI takes over.
